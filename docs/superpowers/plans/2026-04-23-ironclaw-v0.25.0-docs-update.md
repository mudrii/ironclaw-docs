title: Deployment Profiles
description: Pre-configured setting bundles for common deployment scenarios
---

Deployment profiles are named configuration bundles that set sensible defaults for common deployment scenarios. Set `IRONCLAW_PROFILE` to a profile name and it applies a full set of defaults — you only need to override what differs.

Profiles apply before environment variables and `config.toml`. Any setting defined in a profile can be overridden by environment variables or your local config file.

---

## Built-in Profiles

| Profile | Use case |
|---------|----------|
| `local` | Solo developer on a local machine — TUI, libSQL, no sandbox |
| `local-sandbox` | Solo developer with Docker sandbox enabled |
| `server` | Single-user server deployment — PostgreSQL, web gateway, Docker sandbox |
| `server-multitenant` | Multi-user SaaS deployment — higher concurrency limits |

### local

Stripped-down configuration for solo developers working locally. Disables server-oriented features (gateway, heartbeat, routines, sandbox) and enables the TUI.

```bash
export IRONCLAW_PROFILE=local
```

Effective defaults:

| Setting | Value |
|---------|-------|
| `database_backend` | `libsql` |
| `channels.gateway_enabled` | `false` |
| `channels.cli_mode` | `tui` |
| `sandbox.enabled` | `false` |
| `heartbeat.enabled` | `false` |
| `routines.enabled` | `false` |
| `hygiene.enabled` | `false` |

### local-sandbox

Same as `local` but with the Docker sandbox enabled. Requires the Docker daemon to be running.

```bash
export IRONCLAW_PROFILE=local-sandbox
```

Prerequisites: Docker daemon running.

| Setting | Value |
|---------|-------|
| `database_backend` | `libsql` |
| `channels.gateway_enabled` | `false` |
| `channels.cli_mode` | `tui` |
| `sandbox.enabled` | `true` |
| `sandbox.policy` | `readonly` |

### server

Single-user server deployment with PostgreSQL, web gateway, Docker sandbox, and all proactive background features enabled.

```bash
export IRONCLAW_PROFILE=server
```

Required environment variables:

```bash
DATABASE_URL=postgres://user:pass@host/db
```

| Setting | Value |
|---------|-------|
| `database_backend` | `postgres` |
| `sandbox.enabled` | `true` |
| `sandbox.policy` | `readonly` |
| `heartbeat.enabled` | `true` |
| `hygiene.enabled` | `true` |

### server-multitenant

Multi-user SaaS deployment. Builds on `server` with higher concurrency limits and multi-tenant isolation.

```bash
export IRONCLAW_PROFILE=server-multitenant
```

Required environment variables:

```bash
DATABASE_URL=postgres://user:pass@host/db
AGENT_MULTI_TENANT=true
```

Recommended environment variables:

```bash

GATEWAY_AUTH_TOKEN=<secret>
```

| Setting | Value |
|---------|-------|
| `database_backend` | `postgres` |

| `sandbox.enabled` | `true` |
| `sandbox.policy` | `readonly` |

## Usage

Set `IRONCLAW_PROFILE` in your environment or `.env` file before starting IronClaw:

```bash
# In your shell
export IRONCLAW_PROFILE=server

# Or in .env
IRONCLAW_PROFILE=server-multitenant
```

You can override any profile setting with environment variables:

```bash
export IRONCLAW_PROFILE=server
export MAX_PARALLEL_JOBS=3        # Override the profile default
```

Or via `~/.ironclaw/config.toml`.

---

## Configuration Priority

Settings are resolved in this order (highest to lowest):

1. Environment variables
2. `~/.ironclaw/config.toml`
3. Active profile (`IRONCLAW_PROFILE`)
4. Built-in defaults

<Note>
`AGENT_MULTI_TENANT` must be set as an environment variable — it cannot be set via a profile file.
</Note>

## Setup

**Step 1: Get a Composio API key**

Sign up at [app.composio.dev](https://app.composio.dev) and copy your API key.

**Step 2: Store the key in IronClaw**

```bash
ironclaw secret set composio_api_key <your-api-key>
```

**Step 3: Connect apps**

Once the key is stored, ask your agent to connect an app:

```
Connect my GitHub account via Composio
```

The agent will call the `connect` action, which returns an OAuth URL. Visit the URL to authorize the connection.

## Actions

The Composio tool exposes four actions:

| Action | Description |
|--------|-------------|
| `list` | Browse available tools for a given app |
| `execute` | Run a specific tool action |
| `connect` | OAuth-link a third-party app |
| `connected_accounts` | List all linked app accounts |

### list

Browse tools available for an app:

```
What Composio tools are available for Slack?
```

### execute

Run an action on a connected app. The agent selects the correct tool slug automatically:

```
Send a Slack message to #general: "Deployment complete"
```

### connect

Link a new app to your account. Returns an OAuth URL you visit in your browser:

```
Connect my Notion workspace via Composio
```

### connected_accounts

See which apps are currently linked:

```
Show my Composio connected accounts
```

## Security Notes

<Warning>
The Composio API key is stored encrypted in IronClaw's secrets store. It is injected into outgoing requests by the network proxy — it never passes through the WASM module directly.
</Warning>

The Composio tool runs inside IronClaw's WASM sandbox. It can only reach `backend.composio.dev` — no other network access is permitted.

## ACP Job Mode

ACP (Agent Client Protocol) mode lets IronClaw delegate jobs to any compatible external coding agent — Goose, OpenAI Codex, or Gemini CLI.

```bash
# Enable ACP mode
ACP_ENABLED=true

# Optional: memory and time limits
ACP_MEMORY_LIMIT_MB=8192
ACP_TIMEOUT_SECS=3600
```

When `ACP_ENABLED=true`, the `create_job` tool gains an additional `agent_name` parameter. Set it to the name of a configured ACP agent:

```
Create an ACP job using the codex agent to fix the failing tests
```

List configured ACP agents:

```bash
ironclaw acp list
```

<Note>
ACP mode requires the external agent to be installed and accessible from the IronClaw process. The agent runs as a subprocess in the configured sandbox.
</Note>

---

## Per-Job MCP Filtering

Jobs can restrict which MCP servers are active during their execution. This is useful when a job should only use a specific set of tools.

The `create_job` tool accepts an `mcp_servers` array to allow-list specific servers:

```
Create a job using only the github and linear MCP servers
```

Jobs also support a `max_iterations` cap — the maximum number of LLM turns before the job is considered complete. This prevents runaway jobs from consuming unbounded API credits:

| Parameter | Default | Description |
|-----------|---------|-------------|
| `mcp_servers` | all enabled | Allow-list of MCP server names for this job |
| `max_iterations` | unlimited | Maximum LLM turns before job auto-completes |
```

## Commitments

Commitments are a special class of skill that provides active intake — the agent actively watches for new information that matches a commitment and processes it autonomously without being asked.

A commitment is a persistent instruction file that tells the agent:
- **What to watch for** — triggers based on content patterns or time
- **What to do** — an action to take when the trigger fires
- **How often** — a rate limit to avoid over-processing

### Creating a Commitment

Place a `SKILL.md` file in `~/.ironclaw/skills/` with `type: commitment` in the frontmatter:

```yaml
---
name: daily-standup
type: commitment
version: 0.1.0
description: Write a daily standup draft each morning
activation:
  schedule: "0 9 * * 1-5"  # 9am weekdays
---

Every weekday morning, read my memory notes from yesterday and write a standup
draft to memory at daily/standup.md. Keep it to 3 bullet points: done, doing, blockers.
```

### Commitment vs Routine

Commitments and routines are complementary:

| | Routine | Commitment |
|---|---------|-----------|
| **Trigger** | Explicit cron / heartbeat | Passive pattern match or schedule in skill |
| **Setup** | Via agent chat or CLI | Via SKILL.md file in trusted skills dir |
| **Use case** | Operational tasks | Persistent personal assistant behaviors |

Use commitments for behaviors you always want active (e.g., "always summarize long emails") and routines for explicit scheduled tasks (e.g., "generate a weekly report every Friday").
```

## Tool Permissions

IronClaw maintains a persistent per-user permission table that controls whether individual tools require approval on each invocation. This replaces the one-time "allow this tool?" prompts with durable settings.

### Setting Permissions

Use the `tool_permission_set` built-in tool in chat to configure a tool's permission level:

```
Always allow the shell tool without asking
```

```
Require approval every time for the file_write tool
```

Permission levels:

| Level | Behavior |
|-------|----------|
| `always` | Tool runs without any approval prompt |
| `ask` | Tool requires approval on every invocation (default for dangerous tools) |
| `deny` | Tool is blocked — attempts to use it fail immediately |

### Viewing Current Permissions

```
Show my current tool permissions
```

Or via CLI:

```bash
ironclaw tool list --permissions
```

### Resetting Permissions

```
Reset all tool permissions to defaults
```

Permissions are stored per-user in the database and persist across restarts and upgrades.

<Note>
Admin tool policies (set by the instance administrator) take precedence over per-user permissions. An admin can deny a tool for all users regardless of individual settings.
</Note>
```

## 5. Admin Controls

### Admin Tool Policy

Instance administrators can disable specific tools for all users via the `ADMIN_DISABLED_TOOLS` environment variable. Disabled tools are hidden from the agent's tool list and return an error if called directly.

```bash
# Comma-separated list of tool names to disable for all users
ADMIN_DISABLED_TOOLS=shell,file_write,extension_install
```

This overrides per-user tool permissions — even if a user has `tool_permission_set` to `always` for a tool, the admin policy takes precedence.

**Use cases:**
- Shared/public deployments where shell access is inappropriate
- Compliance scenarios requiring audit trails for file operations
- Managed deployments where extension installation should be controlled

### Admin System Prompt

Administrators can inject a system prompt that is prepended to every user's session. This is useful for setting organizational context, policies, or constraints that apply to all users.

```bash
# Path to a markdown file with the admin system prompt
ADMIN_SYSTEM_PROMPT_FILE=/etc/ironclaw/admin-prompt.md

# Or inline (for short prompts)
ADMIN_SYSTEM_PROMPT="You are a customer support assistant for Acme Corp. Do not discuss competitor products."
```

The admin system prompt is prepended before the user's own system prompt (identity file). Users cannot override it.

**Multi-tenant note:** In `server-multitenant` mode, the admin system prompt applies to all tenants. Use per-user workspace isolation for tenant-specific context.
```
